## 対応：前処理の実装

`scripts/lib/prepare_input.py` を追加し、実行スクリプトに組み込んだ。

# 追加検証：前処理導入後の回帰テストと、集計の揺れの発見（2026-09-03）

## 回帰テスト

前処理は全ルーティン共通の処理のため、既存のサンプルデータで在庫監視を再実行し、
数値が変わっていないことを確認した。

| 検証項目 | 前処理 導入前 | 導入後 |
| --- | --- | --- |
| 月あたり金利負担 450,417円 | 一致 | 一致 |
| Z-104 粗利率 6.22% | 一致 | 一致 |
| Z-103 保有185日 / Z-104 保有236日 | 一致 | 一致 |
| 在庫5件 | 一致 | 一致 |
| 元データのチェックサム | 無変更 | 無変更 |
| ログのERROR件数 | 0件 | 0件 |

UTF-8のファイルは前処理でそのままコピーされ、内容も結果も変わらないことを確認。

## 発見した問題：集計の揺れ

回帰テストの過程で、**同じ入力データから実行のたびに違う合計額が出る**ことが判明した。

| 実行 | Z-105（リフォーム費が空欄）の扱い | 想定粗利合計 |
| --- | --- | --- |
| 1回目 | 判定不能（要確認）として金額集計から除外 | 9,110,274円 |
| 2回目 | 「保有日数が短く反響もあり順調」としてA区分に分類し、参考値として合計に算入 | 14,482,792円 |

差額 5,372,518円。どちらの実行もリフォーム費が欠けていること自体は
「不明・要確認」と正しく明記しており、数字の捏造ではない。
しかし**経営レポートとしては、社長が日によって違う数字を見ることになり問題**である。

原因は、プロンプトの「判定の根拠が足りない場合は、無理に分類せず判定不能とする」という
指示が、判断の余地を残していたこと。「保有日数が短いから順調」という別の根拠で
代用する余地があり、金額集計に含めるかどうかも定めていなかった。

## 対応：集計ルールの機械化

`prompts/00_common_rules.md`（全ルーティン共通）と
`prompts/02_inventory_watch.md` に、判断の余地のない形でルールを追加した。

1. 計算に必要な項目が欠けているレコードは、**必ず**判定不能とする。
   保有日数や反響など、別の根拠で代用してはならない。
2. 判定不能のレコードは**金額の合計・平均から必ず除外**する。
   「参考値として含める」ことは禁止。
3. 集計行には**何件中何件で集計し、何を除外したか**を必ず書く。
   例：`想定粗利合計 | 9,110,274円（計算。5件中4件で集計。除外：Z-105＝リフォーム費が空欄）`
4. **件数**の集計（在庫件数・90日超の件数など）には、欠損レコードも含める。
   除外するのは金額の合計・平均のみ。

## 修正後の検証

ルール修正後に同じ入力データで在庫監視を再実行した。

| 実行 | Z-105 の分類 | 想定粗利合計 |
| --- | --- | --- |
| 1回目（修正前） | 判定不能（金額集計から除外） | 9,110,274円 |
| 2回目（修正前） | A：順調（参考値として算入） | 14,482,792円 |
| 3回目（修正後） | 判定不能（金額集計から除外） | **9,110,274円（1回目と一致）** |

集計行にも、指示どおり除外の内訳が出るようになった。

```
想定粗利合計 | 9,110,274円（計算。5件中4件で集計。除外：Z-105＝リフォーム費が空欄）
平均想定粗利率 | 6.36%（計算。想定粗利合計9,110,274円 ÷ 現在販売価格合計143,200,000円。4件で算出）
判定不能（要確認） | 1件 | 21,000,000円（想定粗利計算には不参入）
```

件数と金額の扱い分けも意図どおりに動いた。

- 区分別サマリの件数合計 5件 ＝ 在庫件数5件（判定不能の1件を含む）
- 区分別サマリの金額合計 142,500,000円 ＝ 在庫総額（取得価格ベース）
- 想定粗利の集計だけが4件（Z-105を除外）

元データは無変更、ログのERRORは0件。

## 補足：この問題の性質について

1回目・2回目とも、リフォーム費が欠けている事実は正しく明記されており、
**数字を捏造したわけではない**。問題は「欠損レコードを集計にどう扱うか」が
プロンプトで定まっておらず、実行ごとに判断が変わっていたことにある。

数字の捏造を防ぐルールだけでは、経営レポートとしての信頼性は担保できない。
**同じデータからは同じ数字が出ること**も同等に重要であり、
そのためには判断の余地を残さない機械的なルールが必要だと分かった。

他のルーティン（04 新規案件査定、07 月次経営分析など）でも同種の揺れが
起きうるため、共通ルール（prompts/00_common_rules.md）に規定を置いている。
実データ投入後は、同じ入力で2回実行して合計額が一致するかを
確認することを推奨する。
