# メール自動仕分け・予定登録・エスカレーション（設計と運用）

代表アドレスおよび役員・営業宛のメールを自動で読み取り、
**仕分け → 予定登録 → 代表へのエスカレーション → 返信下書き → 記録** までを行う仕組みです。

判断の主体は常に人間です。この仕組みは「判断材料を整えて、直前まで準備する」役割に徹します。

---

## 1. 前提として確認した事実（重要）

導入前に、実際の環境を調べて分かったことです。設計はこれを前提にしています。

### 1-1. 各人のメールボックスには直接アクセスできない

小林・森・久世それぞれの受信箱に個別にログインすることはできません。
ただし実態として、**業務メールの大半は代表アドレス（`info@…`）宛または CC で集約**されています。
そのため、代表アドレスを起点にすれば実務上ほぼ網羅できます。

> **対応が必要な点**
> 各人が代表アドレスを CC に入れずに送受信したメールは、この仕組みの対象外になります。
> 取りこぼしを無くすには、各人のメールソフト側で
> 「送受信メールを代表アドレスへ自動転送（または常時 BCC）」の設定を入れてください。

### 1-2. サイボウズ Office へは「書き込めない」

サイボウズ Office のスケジュールは、現在 Google カレンダーへ
**読み取り専用の外部カレンダー（ICS 取り込み）** として連携されています。
ICS 取り込みは一方通行のため、**Google カレンダー側から予定を追加してもサイボウズには反映されません。**

| やりたいこと | 現状 | 必要なもの |
| --- | --- | --- |
| サイボウズの予定を読む | ✅ できる（取り込み済み） | — |
| サイボウズへ予定を書く | ❌ できない | サイボウズ Office の API 連携設定（後述） |

**当面の運用**：予定は Google カレンダーに「【要確認】」付きの仮予定として登録します。
サイボウズへの反映は、確定後に人が入力する運用とします。
サイボウズ側への自動登録が必要な場合は、後述の「拡張ロードマップ」を参照してください。

### 1-3. Backlog / kintone への登録には API キーが必要

- **Backlog**：課題の新規作成には API キーが要ります。
  なお Backlog の通知メールに返信すると、その課題にコメントが投稿されます。
  誤投稿を防ぐため、**Backlog からの通知メールは既定で対象外**にしてあり、返信下書きは作りません。
- **kintone**：アプリの API トークンが必要です。未設定なら登録処理は自動的にスキップされます。

## 2. 全体の流れ

```
Gmail（代表アドレス／メンバー宛）
      │
      ▼
 ① 除外判定 …… 営業DM・メルマガ・自動応答・通知系を落とす
      │
      ▼
 ② 内容判定 …… 至急 / 重要 / 要対応 / 情報共有 に分類
      │
      ├─ ③ 日程表現あり → Google カレンダーに【要確認】仮予定を作成
      │
      ├─ ④ 「至急」判定  → 代表（小林）宛のエスカレーション文を作成（既定は下書き）
      │
      ├─ ⑤ 「要対応」判定 → スレッドに返信下書きを作成（送信はしない）
      │
      └─ ⑥ 記録 …… ログシート / Backlog 課題 / kintone レコード
                    ＋ 夕方に当日分のまとめを代表へ
```

## 3. 判定基準

### 3-1. 除外（対象外）

次のいずれかに当たると、以降の処理をせずラベル `AI/対象外` を付けて終わります。

| 条件 | 例 | 例外 |
| --- | --- | --- |
| 自動応答・不在通知 | 「自動応答:」「Out of Office」「配信されませんでした」 | なし |
| 一斉配信・システム通知の送信元 | 求人サイト、SNS、物件情報の一斉配信、Backlog の通知メール | なし |
| 送信専用アドレス（`noreply@` 系） | 各種システムからの通知 | **案件語が2つ以上、または至急語を含めば対象として残す** |
| 営業DM・案内（案件性なし） | 「キャンペーン」「新着」「セミナー」「買取強化中」など | 同上 |

**送信専用アドレスを一律に除外しない理由**：取引先が業務システム経由で送ってくる重要書類
（重要事項調査報告書・管理規約の送付通知など）も `no-reply@` から届きます。
実際のメールで確認したところ、仲介会社からの重調・管理規約の送付が該当しました。
これらは対象として残し、代わりに次の扱いをします。

- 返信しても届かないため、**返信下書きは作りません**
- 本文の署名から担当者のメールアドレスを拾い、報告に「担当者の連絡先」として載せます

### 3-2. 分類

| 判定 | 条件 | 主な処理 |
| --- | --- | --- |
| **至急** | 至急語を1つでも含む | 即時エスカレーション＋返信下書き＋記録 |
| **重要** | 要対応語 かつ 案件語2つ以上 | 記録（Backlog/kintone）＋返信下書き＋夕方のまとめに掲載 |
| **要対応** | 要対応語を含む | 返信下書き＋夕方のまとめに掲載 |
| **情報共有** | 上記以外 | ラベルのみ |

**至急語**：至急 / 緊急 / 本日中 / クレーム / 解約 / 違約 / 契約解除 / 訴訟 / 差押 / 督促 / 内容証明 / 漏水 / 契約不適合 ほか

**要対応語**：ご確認 / ご回答 / ご返答 / ご指示 / ご判断 / ご検討 / ご対応 / いかがでしょうか / 期限 / までに ほか

**案件語**：物件 / 査定 / 買取 / 買付 / 売却 / 仲介 / 媒介 / 重説 / 決済 / 契約 / 内見 / 融資 / 謄本 / 測量 / 境界 / 立退 / 底地 / 共有持分 / 再建築 / 相続 ほか

キーワードは `gas/MailTriage.gs` 冒頭の `MT_KEYWORDS` にまとめてあります。運用しながらここを調整してください。

### 3-3. 日時の読み取り

日程語（打合せ・内見・決済・ご都合 など）を含むメールから日時を抽出します。

| 書き方 | 判定 |
| --- | --- |
| `9月4日 14:00` / `9/4 14:00` | 9/4 14:00 開始の1時間の予定 |
| `2026年9月10日 午後3時` | 9/10 15:00 開始 |
| `9/7 10時半` | 9/7 10:30 開始 |
| `明日15時` / `本日` / `明後日` | 受信日を基準に換算 |
| `9月18日`（時刻なし） | **終日予定**として登録し、件名に「時刻未定」を付す |
| 過去の日付 | 登録しない |
| 電話番号・郵便番号 | 日付として拾わない |

年の記載が無い月日は、受信日から半年以上離れていれば翌年（または前年）と推定します。
この推定を含め、**登録される予定はすべて「【要確認】」付きの仮予定**です。必ず人が確認してください。

## 4. 安全のための決めごと

- **メールは自動送信しない。** エスカレーションもまとめも既定は「下書き作成」です。
  自動送信にするには `ESCALATE_MODE=send` を明示的に設定します。
- **返信は下書きまで。** 返信文は骨組みだけを作り、回答内容は空欄にしてあります。送信は必ず人が行います。
- **既存データを消さない。** ラベル付与と新規作成のみを行い、メール・予定・課題の削除や上書きはしません。
- **同じメールを二重処理しない。** 処理済みラベルと、予定の説明欄に埋め込む識別子で重複を防ぎます。
- **導入時は必ず `previewMailTriage()` から。** 何も作らずに判定結果だけをログに出します。

---

## 5. 導入手順

1. Apps Script プロジェクトを作り、`gas/MailTriage.gs` を貼り付ける。
2. スクリプトプロパティを設定する（`gas/README.md` の一覧を参照）。最低限は次の3つ。
   - `REP_ADDRESSES`：代表アドレス（カンマ区切り）
   - `MEMBER_ADDRESSES`：小林・森・久世のアドレス（カンマ区切り）
   - `BOSS_EMAIL`：エスカレーション先（小林）
3. `previewMailTriage()` を実行し、実行ログで判定結果を確認する。
   **メール・予定・課題は一切作られません**（Gmail のラベルの枠だけが作成されます）。
4. 判定がずれていれば `MT_KEYWORDS` / `NOISE_SENDERS` を調整し、3 を繰り返す。
5. 納得できたら `DRY_RUN=false` にし、`runMailTriage()` を手動で1回実行して結果を確認する。
6. `installMailTriageTriggers()` を実行して定期実行にする（1時間ごと＋夕方のまとめ）。

## 6. 拡張ロードマップ

| # | 内容 | 必要なもの |
| --- | --- | --- |
| 1 | 取りこぼし防止（各人のメールを代表アドレスへ集約） | 各人のメール設定（転送 or 常時 BCC） |
| 2 | Backlog へ自動起票 | Backlog の API キー、対象プロジェクトキー |
| 3 | kintone へ自動記録 | kintone のドメイン、アプリID、API トークン |
| 4 | サイボウズ Office へ予定を自動登録 | サイボウズ Office の API 利用設定（アカウント権限が必要） |

| 6 | 判定を Claude に任せて精度を上げる（キーワードでは拾えない文脈判断） | `docs/mail-triage-routine.md` のルーティン運用 |

## 7. 2つの実装方式

営業日報の自動化と同じく、2通りの実装を併用できます。

| | Claude ルーティン | Apps Script（`gas/MailTriage.gs`） |
| --- | --- | --- |
| 内容の理解 | 文脈まで読んで判断できる | キーワードによる機械的判定 |
| 安定性 | Claude のセッション・コネクタ状態に依存 | Google 側だけで動き続ける |
| 向いている役割 | 判断・要約・返信文の作成 | 除外・ラベル付け・記録・仮予定の量産 |

**推奨は併用**です。Apps Script で確実な下ごしらえ（除外・記録・仮予定）を行い、
Claude ルーティンで「重要」と判定されたものだけを読み込んで判断と文面作成を担当させます。
ルーティンの設定は `docs/mail-triage-routine.md` を参照してください。
